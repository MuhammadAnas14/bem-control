# Bem Control

An IoT device fleet management SaaS platform: ESP32 devices report sensor
telemetry and take remote commands over MQTT/TLS; a multi-tenant web
dashboard and a companion mobile app let a team monitor and manage their
fleet in real time.

This repo is a monorepo with four working pieces - backend, web, mobile, and
firmware - built to actually run together, not standalone demos.

## What it does

- A field technician provisions a new ESP32 in one API call: it gets a
  database record, MQTT broker credentials (scoped so it can only touch its
  own topics), and a QR code - no manual broker configuration per device.
- The device publishes simulated temperature/humidity telemetry over MQTTS
  on a configurable interval, and listens for commands (reboot, push a new
  config, trigger an OTA update).
- The backend ingests that telemetry, persists it, and fans it out live to
  every connected web/mobile client over a WebSocket - a chart on the
  dashboard updates within about a second of a device publishing.
- If a device drops offline unexpectedly (MQTT Last Will), everyone on that
  organization gets a push notification, not just a stale dashboard.
- Everything is scoped to an organization (tenant) - a user can belong to
  more than one, with a role (owner/admin/member) per org.

## Tech stack

| Layer | Choice |
|---|---|
| Backend | Node.js, Express, Prisma, PostgreSQL |
| Messaging | MQTT over TLS, Mosquitto broker (external, via Docker) |
| Realtime | WebSocket (`ws`), fed by the backend's MQTT subscription |
| Web | React, Vite, TypeScript, Tailwind, Recharts, react-leaflet |
| Mobile | React Native, Expo, React Navigation |
| Firmware | C++ (Arduino framework), PlatformIO, PubSubClient, ArduinoJson |
| Push notifications | Expo push API |
| Monorepo | npm workspaces |

## Quickstart

```bash
npm install
npm run certs:generate && npm run infra:up     # Postgres + Mosquitto, with TLS
cd backend && cp .env.example .env             # fill in MQTT_PASSWORD (printed above) + JWT_SECRET
npx prisma migrate dev && npm run dev          # http://localhost:4000

# in another terminal
cd web && cp .env.example .env && npm run dev  # http://localhost:5173
```

Full walkthrough, including the mobile app and firmware, in
**[docs/setup.md](docs/setup.md)**.

## How this gets to ~40% faster prototype-to-production

The time an ad-hoc IoT setup loses going from a bench prototype to a fielded
fleet is almost all manual, per-device work: generating credentials by hand,
editing broker config for each unit, and reflashing firmware to change a
setting. This project's provisioning flow collapses that into:

1. **One API call provisions a device** - DB record, MQTT credentials, broker
   ACL, and a QR code, atomically (`backend/src/services/devices.service.js`).
2. **One firmware image serves the whole fleet** - a device's identity lives
   in a small credentials file populated from that QR code, not in
   per-device firmware variants (`firmware/include/secrets.h.example`).
3. **Config and OTA updates push to the fleet remotely** - a publish
   interval change or a firmware rollout doesn't require physically
   reflashing every unit (`CONFIG_UPDATE` / `OTA_TRIGGER` commands, see
   `docs/mqtt-topics.md`).

## Security notes (dev setup)

- All secrets are read from `.env` files (`.env.example` in each package) -
  none are hardcoded, and `.env`/certs/keys are gitignored.
- MQTT runs over TLS (MQTTS, port 8883); run the REST API behind HTTPS in
  production (plain HTTP is fine for local dev only).
- Every device authenticates with its own MQTT username/password and is
  restricted by broker ACL to its own topics - a leaked device credential
  can't read or spoof another device's data.
- The TLS certificate authority generated by `scripts/generate-dev-certs.sh`
  is a throwaway dev CA, not meant for production use.
