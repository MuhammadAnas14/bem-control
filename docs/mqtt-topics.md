# MQTT topic scheme

Implemented in `backend/src/mqtt/topics.js` (backend) and
`firmware/include/topics.h` (device) - the two must stay in sync since they
address each other by topic name.

Every topic is scoped under a device's own namespace:

```
orgs/{orgId}/devices/{deviceKey}/telemetry
orgs/{orgId}/devices/{deviceKey}/status
orgs/{orgId}/devices/{deviceKey}/commands
orgs/{orgId}/devices/{deviceKey}/config
```

`orgId` is the organization's database ID; `deviceKey` is the device's
public identifier (safe to expose - unlike the API key, it grants no access
on its own). Embedding both in the topic means the backend's single
wildcard subscription (`orgs/+/devices/+/telemetry`) can route an incoming
message to the right tenant/device without an extra DB lookup keyed only on
a bare device ID.

## Authorization

The broker's ACL (generated from `mosquitto/config/acl.conf.template` plus a
per-device block appended at provisioning time, see
`backend/src/services/mqttProvisioning.service.js`) restricts each device's
MQTT username to exactly its own four topics:

```
user device-<deviceKey>
topic write orgs/+/devices/<deviceKey>/telemetry
topic read  orgs/+/devices/<deviceKey>/commands
topic read  orgs/+/devices/<deviceKey>/config
```

The backend's own service account (`bem-backend`) has `readwrite` on `#`
(everything) - it's the trust boundary between all devices, not a peer of
any one device.

## Topics

### `.../telemetry` - device → backend, QoS 1

Published by the device on its configured interval (default 30s, see
`CONFIG_UPDATE` below). Payload:

```json
{ "temperature": 23.6, "humidity": 48.1, "ts": "2026-07-27T15:15:00.000Z", "firmwareVersion": "1.0.0" }
```

Any numeric field other than `ts`/`firmwareVersion` is treated as a metric
and stored as its own `TelemetryReading` row (`metric`, `value`, `unit`) -
adding a new sensor type on the device doesn't require a backend change.
`ts` is optional; if omitted, the backend timestamps the reading on receipt.

### `.../status` - device → backend, retained + Last Will

Payload is the literal string `online` or `offline`. Published:
- `online`, retained, immediately after the device connects and subscribes.
- `offline`, as the MQTT **Last Will and Testament** - the broker publishes
  it automatically if the device disconnects uncleanly (crash, power loss,
  WiFi drop), so the dashboard doesn't show a stale "online" status.

A transition to `offline` from `online` triggers a push notification to
every member of the organization (`backend/src/services/pushNotifications.service.js`).

### `.../commands` - backend → device, QoS 1

Published when a user issues a fleet command (`POST /api/orgs/:orgId/devices/:deviceId/commands`).
Payload:

```json
{ "id": "cmd_123", "type": "REBOOT" | "CONFIG_UPDATE" | "OTA_TRIGGER" | "CUSTOM", "payload": { ... } }
```

- `REBOOT` - device publishes `offline` then calls `ESP.restart()`.
- `CONFIG_UPDATE` - `payload.publishIntervalSeconds` is applied and persisted to flash (NVS).
- `OTA_TRIGGER` - `payload.firmwareUrl` is fetched and flashed via `HTTPUpdate`.

### `.../config` - backend → device, retained

The device's `desiredConfig` (same shape as a `CONFIG_UPDATE` command
payload), republished as a **retained** message whenever it's updated via
`PATCH /api/orgs/:orgId/devices/:deviceId`. Because it's retained, a device
that was offline when the change was made receives it the moment it
reconnects and subscribes - it doesn't need to have been listening live.

## Transport security

All of the above runs over MQTTS (MQTT over TLS) on port 8883. The broker
presents a certificate signed by a dev CA (`mosquitto/certs/ca.crt`,
generated by `scripts/generate-dev-certs.sh`); both the backend
(`backend/src/mqtt/client.js`) and firmware (`firmware/src/main.cpp`)
verify the broker's certificate against that CA rather than skipping
verification. Web/mobile clients don't speak MQTT directly - they get live
updates over a separate authenticated WebSocket (see `docs/api.md`) that the
backend fans out to after ingesting each MQTT message.
